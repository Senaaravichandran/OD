                   advisor recommends, the HOD sanctions, and the student is
                   notified at each step.

================================================================================
4. HOW THE APP WORKS - THE FULL JOURNEY
================================================================================

4.1 STARTUP  (main.dart)
------------------------
1. WidgetsFlutterBinding.ensureInitialized()
2. NotificationService.init()
     - creates the Android notification channel
     - asks for notification permission (Android 13+)
     - loads the "already shown" notification id list from SharedPreferences
3. runApp(SMVECODApp)

SMVECODApp builds:

  ClerkAuth(config: ClerkAuthConfig(...))
    -> MaterialApp
         -> _AppGate

ClerkAuthConfig is given three things:
  publishableKey      identifies the Clerk instance
  redirectionGenerator returns smvecod://auth/callback for OAuth and email-link
                       strategies. Returning a URI here is what makes the Clerk
                       SDK open the DEVICE BROWSER instead of an in-app WebView.
                       This matters: Google refuses OAuth from embedded WebViews
                       ("this browser or app may not be secure"), so the WebView
                       route succeeds on some phones and silently stalls on
                       others.
  deepLinkStream       AppLinks().uriLinkStream filtered to scheme 'smvecod',
                       which feeds the browser's callback back into the SDK so
                       the session is picked up when the user returns.

MaterialApp also registers ClerkSdkLocalizations.localizationsDelegates and
supportedLocales, which the Clerk widgets require.

Theme: Material 3, seed colour #3350B0 (primary blue), secondary #D4A429
(gold), scaffold background #F6F8FD, Roboto.

4.2 THE GATE  (_AppGate in main.dart)
-------------------------------------
_AppGate holds the whole navigation decision in one place. It keeps:

  _currentUser      the app session (AppUser) or null
  _pickedRole       which role button was tapped
  _pendingProfile   (email, regToken, role) when a profile must be filled in
  _restoring        true while the saved session is being read from disk

On init it restores any saved session from SharedPreferences and hands it to
ODService.

It then renders:

  ClerkErrorListener
    -> ClerkAuthBuilder(signedInBuilder / signedOutBuilder)
         -> _buildFlow(...)

_buildFlow decides, in this order:

  1. _currentUser != null            -> the matching dashboard
  2. _pendingProfile != null         -> RegistrationScreen
  3. Clerk says signed in            -> LoginScreen (exchanges the token)
  4. no role picked yet              -> RolePickerScreen
  5. otherwise                       -> AuthScreen for the picked role

IMPORTANT: the role you tap only decides which sign-in options you are shown.
What you are actually allowed to do comes from the profile the server returns.
The app never decides its own permissions.

4.3 ROLE PICKER  (role_picker_screen.dart)
------------------------------------------
The first screen. Three cards:

  Student         "Raise OD requests and track approvals"
  Class Advisor   "Review your class's OD requests"
  HOD             "Give final sanction on recommended ODs"

Tapping one sets _pickedRole and moves to AuthScreen.

4.4 SIGN-IN  (auth_screen.dart)
-------------------------------
What is offered depends on the role:

  STUDENT   "Continue with Google" ONLY.
            There is deliberately no password door for students, because an OD
            is filed against a real, verified college address.

  ADVISOR   "Continue with Google", OR a password form.
            The password form does NOT ask for an email. It shows a dropdown of
            the department's class advisors loaded from the server
            (name + year + section), so the address sent is always one the
            server will accept.

  HOD       "Continue with Google", OR a password form with the HOD address
            pre-filled and read-only.

Google path:
  ClerkAuth.of(context, listen: false).ssoSignIn(context, Strategy.oauthGoogle)
  Because redirectionGenerator is set, this opens the device browser. After
  Google completes, the browser redirects to smvecod://auth/callback, Android
  routes that back into the app, app_links delivers it, and the Clerk SDK
  finishes the session. ClerkAuthBuilder then rebuilds as signed-in.

Password path:
  POST PASSWORD_LOGIN with {role, email, password}.
  Returns either an app session, or needsRegistration + a regToken.

4.5 TOKEN EXCHANGE  (login_screen.dart + clerk_session.dart)
------------------------------------------------------------
Once Clerk reports a signed-in user, LoginScreen runs ClerkSession.exchange():

  1. authState.sessionToken()  -> SessionToken -> .jwt   (the Clerk JWT)
  2. POST CLERK_LOGIN with  Authorization: Bearer <clerk jwt>
  3. The server verifies the JWT, reads the VERIFIED primary email from Clerk,
     enforces the @smvec.ac.in rule, and replies with either:
        - an app session  { user, token }
        - needsRegistration + email + regToken

The app then uses the APP token for every later call. The Clerk JWT is only
ever used for this one exchange. That keeps every other request at zero
external calls.

The screen shows "Signing you in..." while this runs, and on failure shows the
server's message with "Try again" and "Sign out and use another account".

4.6 FIRST-RUN PROFILE  (registration_screen.dart)
-------------------------------------------------
Only students reach this screen. Rostered advisors are created automatically by
the server from the department roster the moment they sign in, and nobody who
is not on that roster is allowed to become an advisor at all.

The form asks for:

  Full name
  Register number
  Year        -> dropdown, built from the server's class list
  Section     -> dropdown, showing ONLY the sections that exist in the chosen
                 year. (Year 2 has a Section D; years 1, 3 and 4 stop at C.)
                 Changing the year clears the section.

  Class advisor -> NOT a question. A read-only panel that fills in as soon as
                   year + section are chosen, showing the advisor that class
                   maps to. The app sends only year and section; the server
                   resolves the advisor from the roster.

Submits REGISTER with {regToken, role, name, rollNumber, year, section} and
receives the app session.

4.7 DASHBOARDS
--------------

STUDENT  (student_dashboard.dart, 1188 lines)
  - Profile banner: name, register number, year, section, department, and the
    class advisor. Tapping the advisor line opens "Correct your class", which
    lists every class with its advisor and calls CHANGE_CLASS. Requests already
    filed stay with the advisor who received them.
  - Three stat chips: Total Requests / Under Review / OD Approved.
  - A card per OD request showing status, event details, advisor and HOD
    remarks, and a 3-step progress stepper:
        Submitted -> Advisor -> HOD
    The stepper turns red at whichever step rejected it.
  - "New OD" bottom sheet (_NewODSheet):
        Class advisor  - read-only, from the profile
        Submission type - SOLO or TEAM
        Team members    - up to 5, first row pre-filled with the student
        Event type      - Hackathon, Internship, Paper Presentation, Workshop,
                          Symposium, Sports, Other
        Event name
        Event date      - date picker; the weekday is computed with
                          DateFormat('EEEE')
        Description
    Submits CREATE_OD. The advisor is NOT sent - the server reads it from the
    student's profile, so a request cannot be routed to someone else's advisor.
  - "Submit result" sheet (_ResultSubmissionSheet), enabled once an OD is
    APPROVED: WON or PARTICIPATION, project name, description -> SUBMIT_RESULT.
  - Pull to refresh.

ADVISOR  (advisor_dashboard.dart, 631 lines)
  - Sees only the requests assigned to them (the server filters, not the app).
  - Filter chips: All Requests / Pending My Review / Approved by Me /
    Rejected by Me, each with a count.
  - A card per request with the student's details and the full event.
  - Approve & Forward, or Reject, each with a remarks field -> ADVISOR_DECIDE.
  - Can update their own class details (year / section / batch) via
    UPDATE_CLASS.
  - Pull to refresh.

HOD  (hod_dashboard.dart, 509 lines)
  - Summary counts: total, approved, rejected.
  - Three tabs:
      Pending      requests already recommended by an advisor
      Approved     sanctioned ODs
      Audit trail  the department-wide action log (HOD only)
  - Review Details -> Approve OD or Reject, with remarks -> HOD_DECIDE.
  - The HOD CANNOT act on a request an advisor has not recommended. The server
    returns 409 and the app surfaces that message.

NOTIFICATIONS SHEET  (notifications_sheet.dart)
  A bottom sheet, opened from the bell icon in every dashboard, listing the
  in-app notifications from the last sync, newest first, with relative times.

4.8 SIGN OUT
------------
_signOut() clears the saved session, resets the shown-notification list, clears
ODService, resets the role picker, and signs out of Clerk if a Clerk session
exists. The user lands back on the role picker.

If the server ever answers 401, ODService fires onSessionExpired, which does
the same clear-down and shows "Your session has expired. Please sign in again."


================================================================================
5. STATE MANAGEMENT
================================================================================

No state-management package is used. There is no Provider, Riverpod, BLoC or
GetX. The app uses only what Flutter ships with:

  setState                 local screen state
  ChangeNotifier           ODService, a singleton that holds the signed-in
                           user's data
  addListener/removeListener  dashboards subscribe to ODService and call
                           setState when it notifies
  Callbacks                _AppGate passes onLogin / onLogout / onUserUpdated
                           down to the screens

ODService is a singleton:

  static final ODService _instance = ODService._internal();
  factory ODService() => _instance;

It holds: the AppUser, the request list, the audit log, the notification list,
the cached advisor list and class structure, a loading flag and the last error.

The server is the single source of truth. Every change is sent to the API and
the record it returns replaces the local copy (_upsert). The app never guesses
what the new state should be.


================================================================================
6. NETWORKING
================================================================================

6.1 ApiClient  (services/api_client.dart)
-----------------------------------------
One method. Every call is a single HTTP POST to the same URL:

  POST {apiBaseUrl}
  Content-Type: application/json
  Authorization: Bearer <token>        (when there is one)

  { "action": "<ACTION>", "payload": { ... } }

  Timeout: 20 seconds.

Responses are JSON. Anything with status >= 400, or success != true, is thrown
as an ApiException carrying the server's own message and the status code.
ApiException.isAuthError is true for 401.

Failure messages are deliberately human:
  timeout        -> "The server took too long to respond. Please try again."
  socket error   -> "Could not reach the server. Check your connection."
  bad JSON       -> "Unexpected server response (<status>)."

6.2 ACTIONS THE APP CALLS
-------------------------
CLERK_LOGIN      Trade a Clerk JWT for an app session.      (Clerk JWT)
PASSWORD_LOGIN   Advisor/HOD password sign-in.              (no token)
REGISTER         Complete a first-run profile.              (regToken in body)
ADVISORS         Advisor list + class structure.            (no token - public,
                 because it is needed before a session exists)
SYNC             Everything this user may see.              (app token)
CREATE_OD        Raise an OD.                               (app token)
ADVISOR_DECIDE   Advisor approves or rejects.               (app token)
HOD_DECIDE       HOD sanctions or rejects.                  (app token)
SUBMIT_RESULT    Student records the outcome.               (app token)
CHANGE_CLASS     Student corrects their class/advisor.      (app token)
UPDATE_CLASS     Advisor updates their class details.       (app token)

6.3 SYNC
--------
One call returns everything the signed-in user is allowed to see:

  requests        filtered server-side by role
                    STUDENT - only their own
                    STAFF   - only those assigned to them
                    HOD     - all, newest first, capped
  notifications   that user's notification list
  auditLogs       HOD only; empty for everyone else

There is NO background polling. Sync runs when a dashboard loads, on pull to
refresh, and when the app is resumed. This keeps the free-tier hosting and
Redis usage low.

================================================================================
9. NOTIFICATIONS  (services/notification_service.dart)
================================================================================

Channel id ....... smvec_od_updates
Channel name ..... "OD updates"
Description ...... "Approvals, rejections and new OD requests."
Importance ....... high
Android icon ..... @mipmap/ic_launcher
iOS .............. alert + badge + sound requested at init

How it works:
  - After every SYNC, ODService passes the notification list to
    NotificationService.showNew().
  - Anything whose id is not already in smvec_seen_notif_ids_v1 is shown, then
    its id is recorded.
  - They are shown oldest first so the newest ends up on top of the shade.
  - The FIRST sync after signing in is silent: the ids are recorded without
    being shown, so a new user is not buried under their entire history.
  - Every call is wrapped in try/catch. A device that refuses notifications
    must never break sign-in.
  - reset() clears the seen list on sign-out, so a different account on the
    same phone starts clean.

LIMITATION - read this before relying on it:
  These are LOCAL notifications. The app raises them itself when a sync finds
  something new, which covers the app being open or resumed. They do NOT arrive
  when the app is fully closed. True push to a closed app needs Firebase Cloud
  Messaging (FCM), which needs a Firebase project and a google-services.json.
  That is not set up.

10. AUTHENTICATION MODEL
================================================================================

Clerk is the only identity provider. The app never stores or checks a student's
password, and it never sends email of its own - Clerk owns email verification.

Trust chain:
  1. Clerk verifies who the person is (Google OAuth).
  2. The app sends Clerk's JWT to the server, once.
  3. The server verifies that JWT against Clerk, reads the VERIFIED primary
     email, and enforces the @smvec.ac.in rule.
  4. The server issues its own short session token; the app uses that from then
     on.

Rules enforced by the server (the app only displays the outcome):
  - Students: Google only, @smvec.ac.in only.
  - Advisors: must be one of the department's 13 rostered addresses. The shared
    staff code alone is not enough, because it would otherwise let any college
    address claim to be an advisor and approve ODs.
  - Two rostered advisors are listed with gmail addresses; they are allowed
    because being on the roster is the department vouching for them. Every
    other non-college address is refused.
  - HOD: recognised by the HOD email address, or the HOD password.

The app holds NO secrets. The Clerk publishable key is public by design. The
staff/HOD passwords are typed by the user and never stored.


================================================================================
11. ERROR HANDLING AND EDGE CASES
================================================================================

- Every server error message is shown to the user as the server wrote it, so
  the app and the portal say the same thing.
- 401 anywhere -> session cleared, back to the role picker, snackbar shown.
- Network failure -> plain-language message, nothing crashes.
- Notification failures are swallowed; they never block sign-in.
- SharedPreferences failures are swallowed; at worst a notification shows twice.
- Changing the year in registration clears the section, so an impossible
  combination (for example Year 1 Section D) cannot be submitted.
- The advisor list failing to load shows a "Try again" button rather than an
  empty dropdown the user cannot get past.
- A student with no advisor on their profile is told so instead of being shown
  a form that will fail.

12. BUILDING AND RUNNING
================================================================================

  flutter pub get
  flutter analyze                 # must be clean
  flutter test                    # validator unit tests
  flutter run                     # debug on a connected device
  flutter build apk --release     # release APK

Output: build/app/outputs/flutter-apk/app-release.apk  (~54 MB)

Pointing the app at a different backend or Clerk instance:

  flutter build apk --release \
    --dart-define=API_BASE_URL=https://your-host/api/mobile \
    --dart-define=CLERK_PUBLISHABLE_KEY=pk_live_xxx

Regenerating the launcher icon after replacing assets/app_icon.png:

  dart run flutter_launcher_icons

ALWAYS RUN `flutter clean` BEFORE A RELEASE BUILD YOU INTEND TO SHIP.
This is not superstition. `flutter build apk` takes the version number from
Gradle but can reuse a stale compiled Dart snapshot, which produced three
releases (2.1.0, 2.2.0, 2.3.0) whose versionCode incremented while the app code
inside did not change at all. The only reliable check is to read the compiled
binary:

  unzip -o -q app-release.apk -d out
  grep -a "Continue with Google" out/lib/arm64-v8a/libapp.so     # must match
  grep -a "Select your Class Advisor" out/lib/arm64-v8a/libapp.so # must not

Note that Dart stores strings containing non-ASCII characters (for example a
curly apostrophe) as UTF-16 in the snapshot, so a plain UTF-8 grep will report
a false miss for those. Check both encodings.

KNOWN LOCAL ISSUE: `flutter test` fails from this directory because the project
path contains an apostrophe ("D:\Project's\..."). Flutter's generated test
harness injects the path into a single-quoted Dart string and the apostrophe
breaks it. The tests themselves pass when the project is copied to a path
without one. Renaming the folder fixes it permanently.

14. CURRENT LIMITATIONS
================================================================================

1. CLERK IS A DEVELOPMENT INSTANCE.
   The publishable key is pk_test_..., so the sign-in screen shows Clerk's
   "Development mode" banner and the instance is capped. Real use by a whole
   department needs a Clerk PRODUCTION instance, which requires CNAME and DKIM
   DNS records on smvec.ac.in.

2. NOTIFICATIONS DO NOT REACH A CLOSED APP.
   See section 9. Needs FCM and a Firebase project.

3. clerk_flutter IS A 0.0.x BETA and community-maintained, not officially
   supported by Clerk. Breaking changes are expected before 1.0.0.

4. THE RELEASE APK IS SIGNED WITH THE DEBUG KEY.
   Fine for sideloading, not acceptable for the Play Store.

5. APK SIZE ~54 MB, driven by the Clerk SDK's transitive dependencies
   (webview, passkeys, image_picker and others).

6. NO OFFLINE MODE. Every screen needs the network; there is no local cache of
   requests beyond what the last sync returned into memory.

7. iOS IS UNVERIFIED. The icons and Info.plist are generated, but the app has
   only been built and tested for Android.
