================================================================================
SMVEC-IT OD - FLUTTER APP
How it works, and everything it is built from
================================================================================

This document covers ONLY the Flutter Android app (the `mobile/` folder). The
Next.js web portal and the API are a separate codebase; they appear here only
where the app talks to them.

App id ........... edu.smvec.it.smvec_od
App name ......... SMVEC-IT OD
Version .......... 3.2.0+11  (versionName 3.2.0, versionCode 11)
Dart package ..... smvec_od
Purpose .......... Students raise On-Duty (OD) requests for events. Their class
                   advisor recommends, the HOD sanctions, the student is pushed
                   a notification at each step, and once an OD is sanctioned the
                   student attaches the certificate or prize photo as evidence.

Written for: whoever maintains or rebuilds this app.


================================================================================
0. WHAT CHANGED IN 3.x
================================================================================

Versions up to 2.4.0 signed in with Clerk and talked to /api/mobile. None of
that remains. 3.x is a different application underneath:

  Identity ......... Clerk            ->  Firebase Authentication
  API .............. /api/mobile      ->  /api/v2
  Database ......... Neon Postgres    ->  Supabase Postgres
  Files ............ none             ->  Supabase Storage (private bucket)
  Push ............. local only       ->  Firebase Cloud Messaging + local
  Reports .......... none             ->  PDF / Excel / Word export
  Staff sign-in .... shared ENV code  ->  one password per staff member

If you install an APK and see Clerk, or a role picker without the three
buttons below, it is a pre-3.0 build. Uninstall it.

================================================================================
3. STARTUP
================================================================================

main() does three things, in this order:

  1. WidgetsFlutterBinding.ensureInitialized()
  2. Firebase.initializeApp(), inside a try/catch
  3. NotificationService.init(), inside a try/catch

Step 2 is wrapped because it is the one thing that can make the app unusable.
If google-services.json is missing from the build, initializeApp throws before
a single pixel is drawn - which on a phone looks like a black screen and tells
nobody anything. Instead the app runs _StartupFailureApp, which says on screen
that sign-in services could not start, shows the error, and tells the person to
reinstall the latest APK. (This actually happened in 3.0.0: the
com.google.gms.google-services Gradle plugin was missing, so google-services.json
was never compiled into the APK. The plugin is now in
android/app/build.gradle.kts and android/settings.gradle.kts.)

Step 3 is optional. A device that refuses notification permission still works.


================================================================================
4. WHO GETS IN, AND HOW
================================================================================

4.1 THE ROLE PICKER  (role_picker_screen.dart)
----------------------------------------------
The first screen offers exactly three choices:

    Student            Class Advisor            HOD

Tapping one only decides which sign-in options the next screen offers. It
grants nothing. What a person is actually allowed to do comes from the profile
the server returns after they authenticate.

4.2 STUDENTS - GOOGLE ONLY  (auth_service.dart)
-----------------------------------------------
A student sees one button: Continue with Google. There is no password field,
because an OD is filed against a real, verified college address.

  - GoogleSignIn is constructed with hostedDomain: 'smvec.ac.in', which makes
    Google's own picker prefer college accounts.
  - _google.signOut() runs first, every time, so the account chooser actually
    appears instead of silently reusing the last account.
  - If the chosen address does not end in @smvec.ac.in the app signs straight
    back out and says which address was picked.
  - The Google credential is exchanged for a Firebase session.
  - FirebaseAuthException codes are translated into sentences a student can act
    on ("No internet connection", "This account has been disabled", ...).

The domain check in the app is a courtesy. The server checks the verified
address on every single call, so a modified app gains nothing.

Google refuses OAuth inside an embedded WebView, which is why this uses the
native google_sign_in flow. The manifest still carries a smvecod://auth deep
link from the browser-based flow used earlier.

4.3 STAFF AND THE HOD - GOOGLE OR PASSWORD
------------------------------------------
A class advisor or the HOD can either use Google with their college address, or
sign in with a password. The password route posts PASSWORD_LOGIN to the server,
which returns a signed staff session token (12-hour life) plus the profile.

Passwords are never in the app. There is no list of staff, no password format
written down in Dart, no shared department code. The app posts what was typed
and the server compares it against a bcrypt digest.

Only the thirteen rostered class-advisor addresses and the HOD address exist as
staff. Nobody can register themselves as a class advisor, from the app or
otherwise - there is no action for it.

4.4 FIRST-TIME STUDENT PROFILE  (registration_screen.dart)
----------------------------------------------------------
A student whose SESSION comes back with needsRegistration is asked for:

    Full name          (pre-filled from the Google account)
    Register number
    Year               (only years the department runs)
    Section            (only sections that year runs)

The class advisor is NOT asked for. The screen shows who the advisor will be
once year and section are chosen, and the server derives the advisor from the
class. A student cannot pick their reviewer.

The year and section lists come from the public CLASSES action, so they are
whatever the department roster says today.

4.5 WRONG CLASS
---------------
A student who registered under the wrong class can correct it from their
profile tab, which calls CHANGE_CLASS. ODs already filed stay with the advisor
who received them.


================================================================================
5. TALKING TO THE SERVER  (api_client.dart)
================================================================================

One endpoint, one shape:

    POST https://od-landing.vercel.app/api/v2
    Authorization: Bearer <token>
    {"action": "...", "payload": {...}}

  - The base URL is overridable at build time:
        flutter build apk --dart-define=API_BASE_URL=https://.../api/v2
  - The token is a Firebase ID token for students, or the signed staff session
    token after a password sign-in.
  - Every call has a 30-second timeout. A timeout and a connection failure get
    different, plain-language messages.
  - A 401 on a student call is retried exactly once with a force-refreshed ID
    token. A session that quietly aged out should not look like a failure.
  - Anything that is not 2xx with success:true becomes an ApiException carrying
    the server's own message, so what the user reads is what the server meant.
  - callPublic() skips the token, for the class list before anyone is signed in.

ACTIONS THE APP USES

  CLASSES          public   the department's year/section grid and advisors
  PASSWORD_LOGIN   public   staff password -> staff session token
  SESSION                   who am I, or needsRegistration
  REGISTER                  first-time student profile
  CHANGE_CLASS              student corrects their class
  SYNC                      requests + notifications (+ audit log for the HOD)
  CREATE_OD                 file a request
  ADVISOR_DECIDE            recommend or reject
  HOD_DECIDE                sanction or reject
  SUBMIT_RESULT             participated / won, prize, project
  UPLOAD_FILE               attach a certificate or photo
  FILE_URL                  a short-lived signed URL for one file
  DELETE_FILE               remove an attachment
  REGISTER_DEVICE           this device's FCM token
  MARK_READ                 clear the notification badge

The app never sends a role, an advisor, a student id or a status it made up.
Scoping is the server's job: SYNC returns only what the caller may see.


================================================================================
6. THE APP'S STATE  (od_service.dart)
================================================================================

ODService is a singleton ChangeNotifier. It holds:

    user, requests, auditLogs, notifications, classes,
    isLoading, lastError

and exposes derived views the screens read directly:

    activeRequests, closedRequests, awaitingMyReview, awaitingHod,
    students (rolled up per register number), requestsFor(registerNumber),
    unreadCount

refresh() calls SYNC and replaces everything. Screens rebuild through
AnimatedBuilder / addListener on the singleton. Every mutating action
(createOd, advisorDecide, hodDecide, submitResult, ...) folds the request the
server returned back into the list, so the UI updates without a second round
trip.

There is no polling. The app syncs on open, on pull-to-refresh, when a push
arrives, and when a push is tapped.

_firstSync distinguishes the initial skeleton load from later refreshes, so a
background refresh does not blank the screen.


================================================================================
7. THE OD WORKFLOW, AS THE APP SEES IT
================================================================================

    Student files            ->  PENDING_ADVISOR
    Advisor recommends       ->  APPROVED_BY_ADVISOR
    Advisor rejects          ->  REJECTED_ADVISOR      (closed)
    HOD sanctions            ->  APPROVED              (closed)
    HOD rejects              ->  REJECTED_HOD          (closed)

The HOD cannot act while a request is still PENDING_ADVISOR. The review sheet
knows this and shows "Waiting for <advisor> to review" with the buttons
withheld, so the person is told why rather than being allowed to tap and fail.
The server refuses it too, and so does a Postgres trigger. Three layers,
because skipping the class advisor is the one thing the department cannot have.

7.1 FILING  (new_od_sheet.dart)
-------------------------------
    Event type      one of seven (Hackathon, Internship, Paper Presentation,
                    Workshop, Symposium, Sports, Other)
    Event name
    First day       a date picker; the day name is derived, not typed
    Number of days  a stepper, 1 to 30
    Last day        derived from the two above, so the range cannot contradict
                    itself. Tapping it is a shortcut that sets the count.
    Description
    Solo or Team    team adds a member list, pre-filled with the student

An OD covers a stretch of days. A symposium running Thursday to Saturday is
one request with day_count 3, not three requests or a note in the description.

7.2 REVIEWING  (review_sheet.dart)
----------------------------------
One sheet serves both the advisor and the HOD; isHod changes the wording and
which action is called. It shows the student, the event, the description, the
result if there is one, the attachments, the advisor's remarks, and then either
the decision controls, the "waiting for the advisor" notice, or "this request
is closed".

Remarks are optional. Left blank, the server writes a sensible default
("Recommended by Class Advisor.").

Approving and rejecting both ask for confirmation first, and the confirmation
says what the student will be told.

7.3 RESULTS  (result_sheet.dart)
--------------------------------
Once an OD is sanctioned the student records the outcome: participated, or won
with a prize. A win must name the prize - the server and a database constraint
both insist.

A result is a claim, so it cannot be filed before the evidence is attached:

    CERTIFICATE     always required
    EVENT_PHOTO     always required
    WINNING_PHOTO   required for a win
    SUPPORTING_DOC  optional

The sheet shows the checklist, attaches in place, and keeps the submit button
disabled until it is satisfied - with the button's own label saying why. The
server applies the same rule, so the block cannot be worked around. Note that
the attachment sheet offers all four kinds regardless of the result: the prize
photo has to go in before the result says there was a prize.

For a team entry, every member's contribution is named here. The department
credits people, not rows, and the server refuses a team result with anyone
unaccounted for.


================================================================================
8. CERTIFICATES AND PRIZE PHOTOS
================================================================================

8.1 WHAT CAN BE ATTACHED  (attachments_sheet.dart)
--------------------------------------------------
    CERTIFICATE           always offered
    WINNING_PHOTO         offered only once the result says the student won
    EVENT_PHOTO           always offered
    SUPPORTING_DOCUMENT   always offered

Sources: camera, gallery, or a PDF from the file picker. Files can be attached
only after the OD is sanctioned - it is evidence of an approved OD, and the
server and a trigger both enforce that.

8.2 COMPRESSION, ON THE DEVICE  (upload_service.dart)
-----------------------------------------------------
A phone camera JPEG is 8-12 MB. The department's connection is not, and the
upload limit is 10 MB, so compression happens before anything leaves the
handset:

  1. flutter_image_compress: fit inside 1600px, quality 80, JPEG,
     autoCorrectionAngle on so a portrait photo is not uploaded sideways.
  2. If the result is still over the limit, a harder second pass at
     1200px / quality 60.
  3. If the compressor cannot read the file at all, the original is sent
     rather than the upload being lost. Compression is a convenience, not a
     gate.

A typical photo lands at a few hundred kilobytes. PDFs are sent as they are.

8.3 UPLOAD, AND READING BACK
----------------------------
The bytes go to UPLOAD_FILE base64-encoded, with the kind, file name and MIME
type. The server compresses nothing further; it checks the type against an
allowlist (JPEG, PNG, WebP, PDF), checks the size, and writes the object to a
PRIVATE Supabase Storage bucket under

    od/<requestId>/<kind>/<uuid>.<ext>

Nothing in the bucket has a public URL. Opening an attachment calls FILE_URL,
which returns a signed URL valid for five minutes, for that one object. The
link does not outlive the screen it was shown on.

8.4 VIEWING  (shared/file_viewer.dart)
--------------------------------------
Images render in-app with pinch zoom. PDFs open in the device's own viewer.
Advisors and the HOD see the same attachments from the review sheet, which is
the point: they are deciding on evidence.

A student can remove their own attachment (DELETE_FILE), which deletes the
stored object as well as the row.


================================================================================
9. NOTIFICATIONS
================================================================================

9.1 PUSH  (push_service.dart)
-----------------------------
The server sends an FCM message whenever an OD changes hands. The app:

  - asks for permission (Android 13+ needs POST_NOTIFICATIONS),
  - registers a background handler, which is what lets a data message wake the
    app at all,
  - on a foreground message, shows it through flutter_local_notifications,
    because Android suppresses the system notification while the app is open,
    and refreshes the OD list behind it,
  - on a tap from the shade, refreshes so the data behind the notification is
    current,
  - posts the device token to REGISTER_DEVICE, and again whenever FCM rotates
    it,
  - deletes the token on sign-out, so the next person to sign in on the same
    phone does not receive the previous user's notifications.

All of it is inside a try/catch. A device without Play Services, or one that
refuses permission, must still be able to use the app.

9.2 LOCAL  (notification_service.dart)
--------------------------------------
Channel: smvec_od_updates. The set of notification ids already shown is kept
in SharedPreferences, so the same approval is not announced twice after a
refresh. reset() clears it on sign-out.

9.3 IN-APP  (notifications_sheet.dart)
--------------------------------------
The bell in every shell shows unreadCount. Opening the sheet lists what SYNC
returned and calls MARK_READ.

    Students      their class's students, rolled up, tap for the history

10.3 HOD  (hod_shell.dart - 6 tabs)

================================================================================
11. REPORTS AND EXPORTS  (reports/, report_export.dart)
================================================================================

The same tab serves all three roles, scoped by what the server already
returned: a student sees their own record, an advisor their class, the HOD the
department. A student is not offered the year and section filters, since they
only ever have one of each.

Search across student name, register number, event, project and prize.
Filters: status, result, year, section, event type, date range.

11.1 ONE RECORD  (report_detail_screen.dart)
--------------------------------------------
Tapping a row opens the record in full: the student, the event and its dates,
the project, the result and prize, the description, the team with each
member's contribution, and the photographs. Any single record can be exported
on its own from here - which is what someone needs when they are sending one
student's achievement rather than a department listing.

11.2 EXPORTING
--------------
Export as -> PDF, Word or Excel. With filters applied the export is what is on
screen; with none it is the whole list.

What goes in: student name, register number, year and section, event, dates
and duration, project, result and prize, description, team members, each
member's contribution, and the photographs. What does not: approval remarks,
who approved when, workflow states. Those belong to the request screens, not
to a record of achievement.

    PDF     one block per record with the photographs embedded.
    Word    a hand-built OOXML package - document.xml, the relationship and
            content-type parts, and word/media for the images, zipped with
            `archive` into a real .docx. Pictures are inline drawings sized to
            3 inches wide, with the aspect ratio read from the image itself so
            nothing is stretched. There is no Word library for Dart; this is
            why `archive` is a dependency.
    Excel   one row per record. A spreadsheet cannot hold the pictures, so the
            photographs are listed by name and the sheet says where to find
            them.

The photographs live in a private bucket, so each one is a signed-URL fetch
before it can go into a document. Gathering is therefore a separate, reported
step - the tab shows "Preparing 4 of 12" rather than freezing behind a
spinner - and a photo that will not download is skipped rather than losing the
whole report. A department-wide export stops fetching after 60 images and
names the rest instead.

Exports are written to Downloads on Android (the app's documents directory
elsewhere), then opened with open_filex or shared with share_plus. The file
name carries the timestamp, so yesterday's export is not overwritten.


================================================================================
12. SECURITY - WHAT THE APP DOES NOT CONTAIN
================================================================================

The app is not trusted for authorization. Everything below is deliberate:

  - No plaintext passwords. Not a staff password, not a format for deriving
    one, not the HOD's. The app posts what was typed; the server compares
    against a bcrypt digest.
  - No database credentials. No Supabase URL, no anon key, no service role
    key, no Postgres connection string. The app cannot reach the database.
  - No storage credentials. Uploads go through the API, which holds the keys.
  - No Firebase Admin private key. The app only ever holds an ID token for the
    person using it.
  - No role claim the app can set. A role comes from the server's profile.
  - No way to become a class advisor or the HOD. There is no action for it.
  - google-services.json is public configuration - the same values any user of
    the APK can read. It is not a secret, and nothing in it authorises anything
    on its own.

What the app does hold on the device: a staff session token (signed by the
server, 12-hour life) and the ids of notifications already shown. Both are
cleared on sign-out. Never a password.

Every rule the UI appears to enforce is also enforced server-side, and the
order of the approval chain is enforced a third time by a Postgres trigger.

13.4 THE STALE SNAPSHOT TRAP
----------------------------
`flutter build apk` can reuse a previously compiled Dart AOT snapshot while
still incrementing versionCode. Three releases (2.1.0, 2.2.0, 2.3.0) shipped
2.0.0's Dart this way, and the version number looked right the whole time.

Always `flutter clean` before a release build, and verify the binary rather
than the version string:

    unzip -p app-release.apk lib/arm64-v8a/libapp.so > /tmp/libapp.so
    grep -a "some string you just added" /tmp/libapp.so
    grep -a "some string you just deleted" /tmp/libapp.so   # must miss

Note: Dart stores non-ASCII strings as UTF-16 in the snapshot, so a UTF-8 grep
for text containing a curly apostrophe will miss even when the code is there.
Pick an ASCII-only string to test with.

13.5 A NOTE ON `flutter test`
-----------------------------
`flutter test` fails in this checkout, and not because of the code: the
apostrophe in the path `D:\Project's\...` breaks Flutter's generated test
harness, which injects the path into a single-quoted Dart string. The tests
pass from a path without an apostrophe. Use `flutter analyze` here, which is
unaffected.

14. FIREBASE PROJECT
================================================================================

Project ............. smvec-od-management
Android app ......... edu.smvec.it.smvec_od
Providers ........... Google (students, staff, HOD)
FCM ................. HTTP v1 API, called by the server with a service account
Config in the app ... android/app/google-services.json

The server verifies ID tokens against Google's published x509 certificates
itself and checks alg, aud, iss, exp, iat and sub, rejecting alg=none. It does
not use the firebase-admin package - that pulls in an ESM-only dependency
(jose, via jwks-rsa) which cannot be require()d in a Vercel function.


================================================================================
15. WHERE THE DATA LIVES
================================================================================

Supabase Postgres, 12 tables: users, staff, class_assignments, students,
events, od_requests, od_team_members, od_approvals, od_results, result_files,
notifications, audit_logs. Plus the od_report_rows view behind the report
screens.

Row level security is enabled on every table with no permissive policies at
all. The API connects as the service role and does its own authorization, so a
leaked anon key reads nothing.

Triggers and constraints enforce, independently of any application code:
  - the HOD cannot decide before the advisor,
  - an advisor cannot decide twice,
  - a closed request cannot change again,
  - a result or an attachment requires an approved OD,
  - a win must name a prize,
  - an OD's last day cannot precede its first, and it cannot run past 30 days,
  - references are OD-<year>-<counter>, unique and gapless per year.

Files live in the private `od-files` bucket: 10 MB cap, MIME allowlist of
JPEG, PNG, WebP and PDF, no public URL, read only through a five-minute
signed URL.


================================================================================
16. KNOWN LIMITS
================================================================================

  - Android only in practice. The iOS folders exist and the Dart is portable,
    but no iOS build has been configured or tested.
  - Debug signing. Fine for sideloading the APK, not for the Play Store.
  - No offline mode. Every screen needs the network; there is no local cache
    of OD data by design.
  - Distribution is a direct APK download from the landing page. There is no
    in-app update check, so a student on an old build stays on it until they
    download again.
  - The student half of the API cannot be exercised by an automated script,
    because it requires a real Google sign-in. The workflow rules behind it are
    tested directly against the database instead.
